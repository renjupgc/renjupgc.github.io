# 改进清单

写给站主自己看的：现状盘点、该补的短板、以及一些可以让站点更有意思的想法。
每条尽量写清楚「为什么」和「怎么落地」，能直接动手的附上命令或文件位置。

## 一、现状速览

| 项 | 数字 |
| --- | --- |
| HTML 页面 | 407（文章 24、棋手 354、赛事 16、工具 5、栏目与首页 6、选拔赛 1） |
| 手写页面 | 约 35 个，其余由 `tools/*.py` 生成 |
| 数据库 | `data/renju.db`：26 场赛事、2561 局、252 人等级分、278 条参赛记录 |
| 有棋谱的对局 | 44 局（`matches.board_record`） |
| 图片 | 173 张、17.4 MB，全为 JPG/PNG，宽度多为 1080px |
| 音频 | 2 首、15 MB，占仓库体积四成 |
| 仓库 | 约 39 MB，无构建产物、无依赖、无 CI |

内容质量是高的：文章有细节、有技术分析，成绩表逐轮可查，等级分有算法说明。
技术侧是「手写为主 + 脚本生成大批页面」的组合，好处是零依赖、零构建、部署即发布，
代价是全站一致性靠脚本自觉维持，缺一层校验。

## 二、本次已落地

都是机械性、可反复执行的改动，不改变视觉与阅读体验：

1. **分享与发现性**：407 页补齐 `canonical` / Open Graph / Twitter Card；
   新增 `sitemap.xml`（407 条）、`robots.txt`、`feed.xml`（RSS，取最新 12 篇）、
   `assets/img/og-cover.png`（1200×630 棋枰分享图）。脚本 `tools/build_seo.py`。
2. **图片**：170 张补齐 `width`/`height`（从文件头读真实像素）、`decoding="async"`，
   首屏之外加 `loading="lazy"`。翻文章时图片不再把正文往下顶。脚本 `tools/build_img_attrs.py`。
3. **404 兜底**：新增 `404.html`，沿用全站样式，指回四个栏目。
4. **流量**：音乐盒 `preload` 由 `auto` 改为 `metadata`——自动播放被拦时不再白拉近 10 MB。
5. **文档**：本文件与 `README.md`（结构、本地预览、构建顺序、写页面的约定）。

## 三、该补的短板

### P0：影响可用性或存在风险

**1. 音频的版权问题**

`assets/audio/` 放的是两首汪峰的完整音轨（《城市之光》《请把我在路上叫醒》），
公开站点上托管未授权音乐，属于明确的侵权风险，也给仓库增加了 15 MB。
到 2026 年这套「进站自动播放」的体验在现代浏览器里也大多被拦，投入产出很差。

建议二选一：
- 换成可商用授权音源（CC0 / Free Music Archive / 自己录的琴声、翻书声）；
- 或者干脆去掉音乐盒，改用 Web Audio 现合成的一声落子音、一次点击的回响，轻、也不涉及版权。

**2. 图片体积**

单篇文章最重的 2.0 MB（`2024-caipan.html`，11 张 1080px 宽 JPG），
全站 17.4 MB。正文显示宽度约 700px，实际投放的分辨率是需要的两倍多。

建议：宽度压到 900px、转 WebP（质量 82），保留原图到仓库外。
预计 17.4 MB → 5 MB 左右，单篇首屏图片从 2 MB 降到 400 KB。
命令（任选其一，需本地装 ImageMagick 或 cwebp）：

```bash
magick mogrify -path out -resize 900x -quality 82 -format webp assets/img/**/*.jpg
```

转完把 HTML 里的 `.jpg` 换成 `.webp` 即可，`build_img_attrs.py` 会自动重读新尺寸。
若想保守，用 `<picture>` 同时保留 JPG 回退，但 407 页改起来不划算——现代浏览器支持率已足够。

**3. 单页过大**

`zayu/t9.html` 205 KB、`zayu/rating.html` 64 KB、`zaji/molun.html` 136 KB。
t9 是一场赛事的成绩表，一次渲染全部组别与轮次。
建议生成时按组别拆成 `<section>` 并默认折叠（`<details>`），或改成前端 `fetch` 一份 JSON 再渲染。
首屏 HTML 可降到 30 KB 以内。

**4. OCR 依赖第三方免费接口**

`zaji/molun.html` 的成绩单识别走 `oai.endpoints.kepler.ai.cloud.ovh.net`（匿名、每分钟 2 次）。
这是别人家的免费额度，随时可能关停或改策略，且带 CORS 依赖。
建议：在界面上说明「识别失败就手动录」，并把返回结果做一次本地校验（人数、轮次、积分是否闭合），
避免错行数据被静默写进计算器。

### P1：影响长期维护

**5. 构建没有单一入口**

六个脚本要按顺序手工跑，顺序错了就产生不一致的页面（比如改了库却忘了跑 `build_players.py`，
成绩表里的姓名会链到不存在的主页）。建议加一个 `tools/build_all.py` 顺序调用，或一个 `Makefile`：

```make
build:
	python tools/build_zayu.py && python tools/build_players.py && \
	python tools/build_qipu.py && python tools/build_predict.py && \
	python tools/build_seo.py && python tools/build_img_attrs.py
```

配一条 GitHub Actions：push 到 `main` 后跑一遍 `build_all.py`，若产物与提交内容不一致就报错。
这一步能把「忘了重建」变成红灯，而不是线上错链。

**6. 缺一致性校验**

生成器与手写页面之间的隐含契约不少，值得写一个 `tools/check.py`：
- 站内链接是否都能落地（407 页里所有 `href`/`src`）；
- 每页是否有 `data-nav`、`<main>`、`#site-header`；
- 棋手页与 `ratings` 表是否一一对应；
- `sitemap.xml` 条目是否与实际文件一致。

几百行以内，跑一次几秒，能挡住绝大多数低级问题（死链、漏页、导航不高亮）。

**7. 搜索只覆盖棋手**

首页搜索框只查 354 位棋手，24 篇文章、16 场赛事都搜不到。
最省事的补法：构建时把 24 篇文章的标题、摘要、正文纯文本压成一份 `assets/search-index.json`
（gzip 后约 60 KB），前端做子串 + 拼音首字母匹配，把现有搜索面板扩展成「棋手 / 文章 / 赛事」三组结果。

**8. 页面模板重复**

文章页的 `<head>`、`article-header`、`article-footer`、`related` 每篇手抄一遍，
25 篇之后还会继续长。可考虑把文章正文抽成 Markdown（或仅正文 HTML 片段）+ front matter，
用 `build_posts.py` 生成整页——与现有「生成器 + 手写」的混合模式一致，
不影响已有页面，只是让新增文章的成本从「复制一页再改」降到「写一段正文」。

### P2：锦上添花

- **深色模式**：`style.css` 已有完整的 CSS 变量（`--paper` / `--ink` / `--line`），
  加一段 `@media (prefers-color-scheme: dark)` 覆盖变量即可，改动限于 30 行。
  纸质暖调在夜里确实刺眼，而站内有长文与打谱，夜读需求真实存在。
- **缓存与预取**：GitHub Pages 不能设缓存头，HTML 约 10 分钟。可在无刷新跳转里对
  鼠标悬停的站内链接做 `fetch` 预取（命中即秒开），成本约 15 行。
- **无障碍**：`aria` 已经写得很细（公告复本 `aria-hidden`、音乐盒 `aria-pressed`），
  还差的是一条 skip-link 和焦点样式检查。
- **`lang` 与排版细节**：正文里的书名号、破折号、数字与英文之间的间距已经不错；
  可加 `text-spacing-trim` 之类的新特性渐进增强，不必强求。

## 四、创意清单

按「能多快做出来」排序，都能复用站内已有的数据与组件。

### 轻：一两天的活

**1. 今日一局**

首页放一局棋，每天换。44 局有棋谱的对局按日期取模即可，直接复用 `board.js` 的渲染与逐手复盘，
配一句话背景（赛事、双方、结果）。访客每次来都有新东西看，也让沉在成绩表里的棋谱重新露面。

**2. VCF 每日一题 + 连胜天数**

`zaji/vcf.html` 已经是现场生成题目，把当天的题按日期做种子固定下来，
做完记一条 `localStorage`，显示「连续 7 天」「最长 12 天」，答错的题进错题本。
成本很低，但给了回访的理由。

**3. 打谱页可分享局面**

把当前手顺编码进 URL（`#p=hhhggg...`），复制链接就能把局面发给别人。
对棋友交流是刚需——现在只能发截图。改动集中在 `zaji/dapu.html` 的初始化与 `hashchange`。

**4. 棋手成绩卡**

棋手主页加一个「存图」按钮，用 Canvas 画一张卡片：姓名、等级分、名次、胜负环、参赛场次、
页脚小二维码（指向该页）。棋友发朋友圈、发群里都需要这样一张图，比截图体面得多。

### 中：一周上下

**5. 等级分时光机**

现在 `ratings` 只是一张快照。但 `matches` 有完整日期与轮次（2561 局，2024-06 至 2026-10），
按赛事顺序重放一遍就能得到每个时点的等级分。
做成滑块：拖动看某个月的榜单，棋手页上画一条自己的等级分曲线。
这是全站数据价值最高的一块，目前只呈现了最后一帧。

**6. 开局命名器**

连珠开局有固定名字（溪月、云雨月、明星、长星……），由前几手的相对坐标决定。
用现有棋谱坐标即可判定，给每局打上开局标签，赛事页按开局分组统计「本站出现最多的开局」。
再进一步，可以按开局反查「谁在这个开局下胜率最高」。

**7. 同型局检索**

每局棋谱转成 225 维落点向量，算余弦相似度，在赛事页给出「与这局最像的另外三局」。
不需要模型，纯几何，几十行 Python 就能算完写进 JSON。

**8. 全站全文搜索**

见 P1-7。做完之后首页搜索框才真正对得起「百宝箱」三个字。

**9. 离线可用（PWA）**

`manifest.json` + 一个 service worker，把 `style.css`、`layout.js`、`board.js`、引擎 wasm 缓存下来。
打谱、禁手、VCF 三个工具离线也能用——棋友常在赛场，网络未必好。
注意：HTML 走「网络优先、失败回落缓存」，否则更新会卡住。

### 重：想清楚再做

**10. 年度回顾页**

每年生成一页：办了多少场、下了多少局、多少位新棋手、最长连胜、最活跃的城市、胜率最高的开局。
数据都在库里，做成图文页，既是给棋友的总结，也是公众号文章的好素材。

**11. 裁判与办赛工具箱**

现有的末轮计算器只解决「最后一轮要什么结果」，往前一步是完整的编排：
瑞士制配对、破同分、轮次表导出、成绩单模板。办赛的人比下棋的人更缺工具，
这一块做扎实，站点的不可替代性会明显提高。

**12. 赛事地理分布**

河南各市参赛人数、办赛场次的分布。**不要用行政区划地图底图**——用地图需要审图号，
个人站点拿不到。改成横向条形图或矩阵热力图（城市 × 年份），信息量一样，也没有合规问题。

## 五、明确不建议做的

- **接入评论、点赞、访问统计**：静态站加这些要引第三方脚本，代价是隐私与速度，
  收益对一个小众资料站有限。真想看数据，用 GitHub 的流量统计或 Cloudflare 的免费分析即可。
- **换框架重写（Next/Astro/Vue）**：现在的零依赖方案已经跑到 407 页且稳定，
  重构的收益主要在开发者体验，而站主的核心诉求是「改内容方便」。先做 P1-8（文章 Markdown 化），
  拿到八成收益，再决定要不要动地基。
- **把所有页面改成客户端渲染**：内容页必须能被搜索引擎和微信抓取，
  现有的「静态 HTML + 局部无刷新」是正确取舍，不要为了手感牺牲可索引性。
